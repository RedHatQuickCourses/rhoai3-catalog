[.lead]
*Selection is not the hard part. Making the selection safe, fast, and repeatable is.*

In the early days of Generative AI, teams solved the “model problem” the same way they solved everything else: search the internet, download weights, and hope for the best.

That approach collapses in production.

* A model that performs well on paper may not fit your hardware.
* A model with the wrong license can block an entire product launch.
* A model served from the wrong source can turn “Time-To-First-Token” into “Time-To-First-Customer.”

This is the **Model Catalog** problem: not discovery, but **curation**.

[NOTE]
.The Core Sales Objection
====
*"Why do we need a Model Catalog? Can't data scientists just use Hugging Face?"*

Discovery is easy. **Enterprise deployment is expensive.** The Model Catalog exists to reduce deployment risk by providing curated, validated options with known performance characteristics and a streamlined deployment path.
====

== The Solution: The Model Catalog

In **Red Hat OpenShift AI (RHOAI) 3.2**, the Model Catalog is the centralized discovery hub for Generative AI models.

It is not a replacement for the Model Registry.

* **Model Catalog**: *Find and choose* models that are validated and deployment-ready.
* **Model Registry**: *Track and govern* the specific models your organization has selected, versioned, and promoted through environments.

The catalog is the “showroom.” The registry is the “title office.”

== What the Catalog Delivers (In Practice)

The Model Catalog aggregates models from major providers and ecosystems, including:

* Red Hat
* IBM
* Meta
* NVIDIA
* Mistral AI
* Google

It also adds two things that raw public hubs do not guarantee:

=== 1. Validated Performance (“No Surprises”)

The catalog includes performance metrics and benchmarks verified by Red Hat so teams can compare models against hardware realities before deployment.

* **The win:** predictable deployment behavior.
* **The benefit:** fewer failed pilots, fewer GPU “black hole” deployments, faster time-to-value.

=== 2. Deployment Defaults (“The Fast Path”)

RHOAI 3.2 includes a streamlined deployment wizard that provides sensible defaults for common deployment parameters.

* **The win:** fewer knobs, fewer mistakes.
* **The benefit:** platform engineers spend less time debugging “wizard drift” across projects.

=== 3. ModelCars (“Ship Models Like Software”)

Many validated catalog models are delivered as **ModelCars**—models packaged as OCI artifacts (container images).

* **Recommendation:** In RHOAI, prefer ModelCar images hosted on `registry.redhat.io` over raw object storage downloads.
* **Benefits:** layer deduplication, faster startup times, simpler distribution inside enterprise networks.

== Your Mission: Operate the Showroom

In this course, you will take on the role of a platform engineer responsible for making the catalog usable, trustworthy, and operationally stable.

**You will execute the following technical workflow:**

1. **Architecture:** Understand how the catalog is built, how it differs from the registry, and how model artifacts are represented (ModelCars, quantization variants).

3. **Administration:** Control visibility and sources by configuring the catalog service and its backing ConfigMaps.
4. **Reliability:** Apply the known fixes and constraints for RHOAI 3.2 (upgrade issues, name limits, storage option behavior).

== Architecture: How the Model Catalog Works
:navtitle: Architecture Deep Dive
:toc: macro

// Antora metadata
:page-role: architecture-concept
:description: Technical deep dive into Model Catalog components, sources, and how catalog choices connect to deployment.

[.lead]
*A catalog is not a database. It is a control surface.*

Platform engineers operate the Model Catalog like an air-traffic system:

* It must present the right options (curation).
* It must guide users into safe defaults (deployment wizard).
* It must reflect infrastructure reality (hardware profiles, quotas, and runtimes).

== 1. Catalog vs. Registry (Two Different Jobs)

The Model Catalog and Model Registry solve different problems:

* **Model Catalog:** discovery and selection of validated models
* **Model Registry:** tracking, versioning, and governance of models your organization has adopted

Think of it this way:

* **Catalog:** “Which model should we choose?”
* **Registry:** “Which exact model version did we deploy, and why?”

== 2. What’s Inside a Catalog Model Card

Each model entry in the catalog typically includes:

* **Provider / family:** Granite, Llama, Mistral, Qwen, Phi, etc.
* **Validated variants:** quantized formats (INT4, INT8, FP8) appropriate for different hardware
* **Performance context:** benchmarks and metrics verified for specific configurations
* **Artifacts:** the actual model reference used at deployment time

In OpenShift AI, the artifact reference is often a **ModelCar** (OCI artifact).

== 3. ModelCars (OCI Artifacts) — The Default “Enterprise” Distribution

RHOAI uses **ModelCars**: model artifacts packaged as OCI container images (hosted on `registry.redhat.io`).

This matters operationally:

* **Faster cold starts:** image pulls and layer caching outperform raw weight downloads.
* **Layer deduplication:** shared layers reduce bandwidth and storage cost.
* **Predictable supply chain:** enterprises already know how to mirror, sign, and scan container images.

[IMPORTANT]
====
If you are using RHOAI, prefer **ModelCar images** over ad-hoc downloads from public hubs or raw S3 pulls whenever possible.
====

== 4. How Catalog Selection Connects to Deployment

In RHOAI 3.2, the catalog’s deployment workflow is optimized for speed:

1. **Select a model** from the catalog
2. **Launch the deployment wizard**
3. **Choose a project and a serving runtime**
4. **Match hardware profiles** to the model’s requirements
5. **Deploy** (creating KServe resources behind the scenes)

== 5. Integration with Hardware Profiles (Infrastructure Reality)

The catalog does not magically create GPUs. It must align with what your cluster can provide.

* **Auto-selection:** The system attempts to pick a serving runtime that matches the model type and your available hardware profiles (for example, CUDA-based runtime for NVIDIA GPUs).
* **Minimum requirements:** some models require specific accelerator classes (A100/H100 or AMD MI300) and may only be deployable with certain quantized variants.

== 6. Administration Surface (Sources and Visibility)

Administrators control:

* **Whether the catalog is visible** in the dashboard
* **Which catalog sources are presented** to users (for example, curated vendor sources, internal sources, or restricted sources)

In RHOAI, the catalog sources are configured via Kubernetes resources (ConfigMaps), which allows GitOps-style management.

== Lab: Using the Deployment Wizard Safely
:navtitle: The Deployment Wizard
:toc: macro

// Antora metadata
:page-role: hands-on-lab
:description: Deploying a validated model from the Model Catalog in RHOAI 3.2 using safe defaults and known constraints.

[.lead]
*A fast deployment is only valuable if it is repeatable.*

In this lab, you will deploy a validated model from the **Model Catalog** using the RHOAI 3.2 deployment wizard. Along the way, you will apply the guardrails that prevent the most common “wizard accidents.”

[IMPORTANT]
.Prerequisites
====
* Access to the OpenShift AI 3.2 dashboard
* Permissions to create resources in a Data Science Project
* At least one appropriate Hardware Profile (CPU or GPU) available in the cluster
====

== Step 1: Open the Model Catalog

1. Open the **OpenShift AI Dashboard**
2. Navigate to **AI hub → Catalog**
3. Use filters to narrow the selection by:
   * provider
   * model family (Granite, Llama, Mistral, Qwen, Phi)
   * quantization (INT4/INT8/FP8)

== Step 2: Select a Validated Model Variant

Choose a model variant that matches your hardware and your deployment goal:

* **Small model / quick validation:** Granite 3.x small variants
* **GPU-constrained environments:** INT4/INT8 variants
* **Modern accelerators:** FP8 variants (notably relevant for AMD GPUs supporting FP8 and GGUF variants)

[NOTE]
.ModelCars vs. Raw Downloads
====
When available, the catalog will point to **ModelCar (OCI) artifacts** hosted on `registry.redhat.io`.

Prefer these over raw downloads because they start faster, deduplicate layers, and fit enterprise image distribution patterns (mirroring, scanning, signing).
====

== Step 3: Launch the Deployment Wizard

From the model card:

1. Click **Deploy**
2. Select the target **Data Science Project**
3. Choose the **serving runtime** (or accept auto-selection)
4. Choose a **Hardware Profile** that matches the model’s requirements

== Step 4: Apply the Two Critical Guardrails

=== Guardrail A: Name Length (63 characters)

If the wizard generates a long resource name, shorten it.

* **Why:** Kubernetes DNS label limits can silently break deployments when KServe appends suffixes.
* **Rule of thumb:** keep names under ~30–40 characters.

Examples:

* `mistral-small-24b-awq`
* `llama-3-8b-int8`

=== Guardrail B: Storage Options in New Projects

If you do not see “Existing cluster storage” in a brand-new project:

* Create a **Data Connection** first in that project (even a simple URI connection).
* Return to the wizard and retry.

== Step 5: Deploy and Validate

After confirming the wizard settings, deploy the model.

Validate success using both the UI and CLI:

[source,bash]
----
# Check created KServe resources (names vary by UI flow)
oc get inferenceservices -n <project-namespace>

# Check pods and events
oc get pods -n <project-namespace>
oc get events -n <project-namespace> --sort-by=.lastTimestamp | tail -n 20
----

== Step 6: Confirm Hardware Alignment

If you deployed to GPU:

[source,bash]
----
oc get pods -n <project-namespace> -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[*].resources.limits.nvidia\\.com/gpu}{"\n"}{end}'
----

*Expected:* pods requesting GPU resources only if a GPU profile was selected.

== Administration & Configuration (Curating the Showroom)
:navtitle: Administration & Configuration
:toc: macro

// Antora metadata
:page-role: platform-admin
:description: How to enable/disable the Model Catalog, configure sources, and manage access patterns in OpenShift AI 3.2.

[.lead]
*If users can’t trust what they see, they won’t use it.*

The Model Catalog is enabled by default, but it is not “set and forget.”

As a platform engineer or administrator, you own:

* what sources appear
* what models are promoted as “deployment-ready”
* how the catalog behaves after upgrades
* the boundary between catalog visibility and deployment permissions

== 1. Enable / Disable the Model Catalog in the Dashboard

If you need to hide the catalog UI (for example, during a migration window), update the `OdhDashboardConfig` resource.

* **Hide the catalog menu:** set `spec.dashboardConfig.disableModelCatalog` to `true`

[source,bash]
----
oc get odhdashboardconfig -n redhat-ods-applications
----

[source,bash]
----
oc patch odhdashboardconfig odh-dashboard-config -n redhat-ods-applications --type merge -p '{
  "spec": { "dashboardConfig": { "disableModelCatalog": true } }
}'
----

To re-enable, set it back to `false`.

== 2. Configure Catalog Sources (What Users See)

The catalog sources are configured via a ConfigMap (file-based configuration).

The key object:

* **Namespace:** `rhoai-model-registries`
* **ConfigMap:** `model-catalog-sources`

[source,bash]
----
oc get configmap model-catalog-sources -n rhoai-model-registries -o yaml
----

=== Source Model (Two Logical “Files”)

Like other RHOAI components, the ConfigMap often contains two logical “files”:

1. **`sources.yaml`**: defines which catalogs are loaded
2. **`<your-catalog>.yaml`**: defines models and their artifacts

[%collapsible]
====
[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: model-catalog-sources
  namespace: rhoai-model-registries
data:
  sources.yaml: |
    catalogs:
      - name: "Enterprise Catalog"
        id: "enterprise-catalog"
        type: "yaml"
        properties:
          yamlCatalogPath: "/data/user-sources/enterprise-models.yaml"

  enterprise-models.yaml: |
    models:
      - name: "granite-3.x-instruct"
        description: "Validated Granite family model (ModelCar)"
        customProperties:
          model_type:
            metadataType: MetadataStringValue
            string_value: "generative"
          provider:
            metadataType: MetadataStringValue
            string_value: "IBM"
          format:
            metadataType: MetadataStringValue
            string_value: "modelcar-oci"
        artifacts:
          - name: "model-artifact"
            uri: "oci://registry.redhat.io/redhat-ai-services/modelcar:granite-3.x-instruct"
----
====

[IMPORTANT]
====
If you are using ModelCars, ensure your cluster can pull from `registry.redhat.io` (credentials/mirroring) as required by your environment.
====

=== Apply Changes and Force Reload

After changes:

[source,bash]
----
oc delete pod -l component=model-catalog -n rhoai-model-registries
oc get pods -l component=model-catalog -n rhoai-model-registries -w
----

== 3. Access Control: Visibility vs. Deployment Rights

The catalog can be visible, but deployments still require:

* project access (RBAC)
* quotas
* hardware capacity (matching hardware profiles)

This is intentional: the catalog is for discovery, while deployment is a governed action.

== 4. Hardware Profiles Integration (The Safety Net)

When users deploy from the catalog, RHOAI attempts to:

* pick a compatible runtime based on the model
* align deployment settings to the selected hardware profile

As a platform engineer, your role is to keep hardware profiles accurate and available so auto-selection works reliably.

== Troubleshooting & Known Constraints (RHOAI 3.2)
:navtitle: Troubleshooting & Constraints
:toc: macro

// Antora metadata
:page-role: troubleshooting-guide
:description: How to debug Model Catalog issues in OpenShift AI 3.2 and work around current platform constraints.

[.lead]
*A catalog that does not load is worse than no catalog at all.*

The Model Catalog is the front door to your GenAI platform. When it fails, users do not “deploy slower”—they deploy *elsewhere*.

This section provides the operational playbook for the most common Model Catalog failures in **Red Hat OpenShift AI 3.2**, along with the known product constraints you must design around.

== 1. Upgrade Initialization Failure (“Request access to model catalog”)

After upgrading from OpenShift AI 2.24 to 3.2, some clusters encounter an initialization issue where the catalog fails to load and the UI displays:

*`Request access to model catalog`*

=== Root Cause (What’s Happening)

The catalog service depends on the `model-catalog-sources` ConfigMap and a healthy `model-catalog` deployment. During some upgrades, the existing ConfigMap or deployment state is incompatible with the new service expectations.

=== Fix (Force a Clean Refresh)

[IMPORTANT]
====
This is a **safe reset** of the catalog service configuration. It does not delete your models. It forces the catalog to recreate its configuration state.
====

. **Delete the ConfigMap and deployment:**
+
[source,bash]
----
oc delete configmap model-catalog-sources -n rhoai-model-registries
oc delete deployment model-catalog -n rhoai-model-registries
----

. **Wait for the catalog pod to recreate and become ready:**
+
[source,bash]
----
oc get pods -n rhoai-model-registries -l component=model-catalog -w
----

. **Re-check the UI:** Navigate to **AI hub → Catalog**.

== 2. Silent Deployment Failure (Name Length > 63 Characters)

Some models have long names (for example, variants of Mistral or Qwen). When you deploy from the wizard, KServe appends suffixes, and the resulting Kubernetes resource names can exceed the 63-character DNS label limit.

=== Symptom

* The wizard completes, but resources do not appear (or fail without an obvious error).
* The underlying KServe resources fail validation.

=== Workaround

* **Manually shorten the deployment name** in the wizard before creating resources.
* Use a stable naming convention:
  * `granite-3-2b`
  * `llama-3-8b-int8`
  * `mistral-small-24b-awq`

== 3. Missing “Existing cluster storage” Option in New Projects

When deploying from the catalog into a **new** Data Science Project, the wizard may not show the “Existing cluster storage” option.

=== Root Cause

The project does not yet have any **Data Connections** defined. The wizard hides some storage options until at least one connection exists.

=== Fix

* Create a simple Data Connection first (even a URI-based one):
  1. Open the OpenShift AI Dashboard
  2. Go to **Settings → Data connections**
  3. Create a Data Connection in the target project
* Return to the Model Catalog wizard and retry the deployment.

== 4. Catalog Visibility vs. Deployment Authorization

The catalog can be visible to many users, but deployments still fail if the user lacks:

* Project membership
* Required quotas
* Access to the target hardware profile / accelerator capacity

=== Quick Checks

[source,bash]
----
# Can the user create resources in the target namespace?
oc auth can-i create inferenceservices -n <project-namespace>

# Is there capacity for GPUs?
oc get nodes -l nvidia.com/gpu.present=true
----

== 5. Operational Best Practices

* **Prefer ModelCars (OCI artifacts):** Use ModelCar images from `registry.redhat.io` when available. They reduce cold-start time and simplify distribution.
* **Treat catalog sources as code:** Manage `model-catalog-sources` via GitOps wherever possible.
* **Standardize names:** Enforce short, predictable deployment names to avoid Kubernetes limits and reduce operational ambiguity.
