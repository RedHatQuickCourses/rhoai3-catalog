*To the user, it is a gallery. To the engineer, it is a supply chain.*

Before you operate the catalog, you must understand the machinery that powers it. The Model Catalog is not just a list of hyperlinks; it is an integration engine that connects trusted content to your infrastructure using three specific technical primitives:

1.  **The Content:** Red Hat Validated Models (Risk Reduction).
2.  **The Delivery:** ModelCars (OCI Artifacts).
3.  **The Optimization:** Quantization Profiles (TCO Control).



== 1. Red Hat Validated Models (The "Trust" Engine)

A raw model on a public hub is a black box. It might have malicious code in its tokenizer, or it might hallucinate excessively on your specific hardware.

A **Red Hat Validated Model** is a known quantity. Before a model appears in the catalog with the "Red Hat" badge, it undergoes a rigorous qualification process:

* **Security Scanning:** The model weights and code are scanned for known CVEs and malicious injection patterns.
* **Hardware Verification:** The model is tested on specific hardware profiles (e.g., NVIDIA A100, L40S, AMD MI300) to ensure it does not fail with obscure CUDA errors.
* **Performance Benchmarking:** Red Hat engineers run standard benchmarks (like *GuideLLM*) to establish baseline throughput (tokens/sec) and latency numbers.

**The Engineering Value:** You don't have to waste weeks "qualifying" a model. If it's in the catalog, it runs.

== 2. ModelCars: OCI-Based Delivery

The most significant architectural shift in OpenShift AI is the move away from "safetensors in S3 buckets" toward **ModelCars**.

A **ModelCar** is a Large Language Model (LLM) packaged as an OCI (Open Container Initiative) image. It treats model weights exactly like software binaries.

* **Structure:** The model weights (`.safetensors`, `.gguf`) are stored in the filesystem layer of a container image.
* **Delivery:** When a user deploys a model, the cluster pulls this image from `registry.redhat.io` using the standard container runtime (CRI-O).
* **Operational Benefits:**
    * **Deduplication:** Updates to a model family often share base layers, reducing storage costs.
    * **Caching:** Once a node pulls a 70B model, it is cached locally. Subsequent deployments on that node are near-instant.
    * **Air-Gap Friendly:** You can mirror these images to your private registry (Quay) using standard `oc mirror` commands.

== 3. Quantization Strategies (The TCO Engine)

This is the most critical concept for cost control. The catalog offers models in specific "Quantized" formats. Understanding these suffixes is the difference between a $50,000/year cluster and a $200,000/year cluster.

[cols="1,1,2", options="header"]
|===
| Suffix | Precision | Operational Impact

| **.w4a16**
| **4-bit Weights / 16-bit Activations**
| **Best for VRAM Constraints.** Allows larger models (e.g., 70B) to fit on standard enterprise GPUs (like A10g) while maintaining reasonable accuracy.

| **.w8a8**
| **8-bit Weights / 8-bit Activations**
| **Balanced Performance.** Good speed and memory savings; widely supported on most modern GPUs.

| **.FP8**
| **8-bit Floating Point**
| **High Performance.** Designed for modern accelerators (NVIDIA H100, Ada Lovelace) that have native FP8 support. Offers the best balance of speed and accuracy if your hardware supports it.
|===

**The Takeaway:** When you select a model in the simulation, look at the suffix. If you are deploying to a smaller GPU, you *would* choose **w4a16**.
