Administration & Troubleshooting

If users can’t trust what they see, they won’t use it.

The Model Catalog is enabled by default, but it is not "set and forget." As a Platform Engineer, you own the curation of this surface. You decide which sources are visible, how the catalog handles maintenance windows, and how to resolve infrastructure conflicts.

This section covers the administrative primitives (ConfigMaps, CRDs) and the "Break-Glass" troubleshooting procedures for RHOAI 3.2.

1. Controlling Visibility (The "Kill Switch")

There are scenarios—migrations, upgrades, or security audits—where you need to temporarily disable user access to the catalog. You control this via the OdhDashboardConfig resource.

To hide the catalog from the UI:

# Patch the dashboard config to disable the catalog menu item
oc patch odhdashboardconfig odh-dashboard-config \
  -n redhat-ods-applications \
  --type merge \
  -p '{"spec": {"dashboardConfig": {"disableModelCatalog": true}}}'

To restore access: Set disableModelCatalog back to false.

2. Configuring Sources (Curation as Code)

The catalog is not hardcoded; it aggregates sources defined in a Kubernetes ConfigMap. This allows you to manage your catalog sources via GitOps.

  • Namespace: rhoai-model-registries

  • Object: ConfigMap model-catalog-sources

To view or edit current sources:

oc get configmap model-catalog-sources -n rhoai-model-registries -o yaml

Adding a Private Source

You can add your own internal catalog (e.g., a curated list of fine-tuned company models) by appending a source block to this ConfigMap:

sources:
  - sourceURI: https://github.com/my-org/my-curated-catalog/archive/refs/heads/main.zip
    name: internal-finance-models
    displayName: "Acme Finance Models (Curated)"
    description: "Verified models for financial sentiment analysis."
The Reload Process

The catalog service caches these sources. After editing the ConfigMap, you must force a reload by deleting the catalog pods: oc delete pod -l component=model-catalog -n rhoai-model-registries

3. Troubleshooting Playbook (RHOAI 3.2)

These are the three most common failure modes encountered by platform engineers in the current release.

Issue A: The Upgrade Hang ("Request access to model catalog")

  • Symptom: After upgrading from RHOAI 2.x to 3.2, the Catalog UI is blank and displays an error: "Request access to model catalog."

  • Root Cause: The model-catalog-sources ConfigMap structure changed between versions, and the upgrade operator did not cleanly reconcile the old state.

  • The Fix: Force a regeneration of the default configuration.

# 1. Delete the existing ConfigMap
oc delete configmap model-catalog-sources -n rhoai-model-registries

# 2. Restart the operator (it will recreate the ConfigMap with correct defaults)
oc delete pod -l name=model-registry-operator -n redhat-ods-monitoring
# (Note: Namespace may vary depending on operator install mode)

Issue B: The "Missing Storage" Loop

  • Symptom: In the Deployment Wizard, the "Existing Cluster Storage" option is hidden or disabled, forcing you to create a new connection even if PVCs exist.

  • Root Cause: The Wizard UI logic hides the "Existing Storage" radio button if it detects zero DataConnections in the project.

  • The Fix:

    1. Navigate to Settings → Data Connections.

    2. Create a "Dummy" connection (it doesn’t need to be real).

    3. Refresh the Wizard. The "Existing Cluster Storage" option will now appear.

Issue C: DNS Name Collisions

  • Symptom: Deployment status stays in "Unknown" or "Failed" with internal server errors regarding Service creation.

  • Root Cause: The user accepted the default model name (e.g., mistral-7b-instruct-v0.1-quantized-w4a16). KServe appends suffix strings (e.g., -predictor-default) which pushes the total character count over the Kubernetes 63-character DNS label limit.

  • The Fix: Enforce a naming convention. Rename deployments to use short aliases (e.g., mistral-7b-lab).

4. Operational Guardrails Summary

To ensure a stable "Showroom" for your users, adopt these three rules:

  1. Prefer ModelCars: Ensure your cluster has pull secrets for registry.redhat.io. This enables the OCI-based artifact workflow (deduplication/caching).

  2. GitOps the Sources: Do not manually edit the model-catalog-sources ConfigMap in production. Store the file in Git and apply it via ArgoCD/Tekton to prevent drift.
