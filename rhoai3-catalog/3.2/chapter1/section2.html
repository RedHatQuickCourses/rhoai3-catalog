Lab: Using the Deployment Wizard Safely

A fast deployment is only valuable if it is repeatable.

In this lab, you will deploy a validated model from the Model Catalog using the RHOAI 3.2 deployment wizard. Unlike a manual kubectl apply of a raw KServe YAML, the wizard enforces consistency—but it still requires operator judgment to avoid common platform constraints.

You will select a model, align it with a hardware profile, and apply specific guardrails to prevent downstream DNS and storage errors.

Prerequisites

  • Access to the OpenShift AI 3.2 Dashboard.

  • A Data Science Project created (e.g., my-llm-project).

  • Critical: A pre-existing Data Connection (S3/Minio) in that project (required to unlock storage options in the wizard).

Step 1: Filter and Select

The catalog view can be noisy. Use the filters to isolate validated, hardware-optimized assets.

  1. Navigate to AI Hub → Model Catalog.

  2. In the filter sidebar, select:

    • Provider: Red Hat (to see validated models).

    • Model Family: Select Granite or Mistral (depending on available inventory).

  3. Select the Variant: Click on a model card (e.g., granite-3.1-8b-instruct).

Operational Tip: Check the Source

Inspect the Product Version or Source field in the model card. * If it references registry.redhat.io, this is a ModelCar (OCI). It will pull fast and cache efficiently. * If it references a URL, it may be a direct download (slower startup).

Step 2: Configure the Runtime (The Wizard)

Click Deploy to enter the configuration flow.

1. Project Selection

Select your target Data Science Project.

2. Guardrail A: Name Length

The wizard auto-generates a name based on the model. You must truncate this.

  • The Constraint: Kubernetes DNS labels have a strict 63-character limit. KServe appends suffixes (e.g., -predictor-default) to creating service names.

  • The Risk: If the model name is ~50 chars, the appended suffix will break the deployment limit, causing a silent failure in the Service Mesh.

  • The Action: Rename the deployment to something short.

  • Bad: granite-3-1-8b-instruct-quantized-w4a16

  • Good: granite-8b-lab

3. Guardrail B: Storage & Connection

  • Scenario: You see the "Model Location" section.

  • The Trap: If you created a new project but did not create a Data Connection, the wizard may lock you into "New Data Connection" mode or fail to list "Existing Cluster Storage."

  • The Fix: Ensure you have a valid S3/Object Store connection selected. This is where the model (if not a ModelCar) would be downloaded to, or where the serving runtime will look for configuration.

Step 3: Align Hardware Profiles

This is the most critical step for system stability.

  1. Look for the Compute resources section.

  2. Hardware Profile: Select the profile that matches the model’s quantization.

    • For a .w4a16 model, a standard GPU profile (e.g., NVIDIA L4 or A10g) is sufficient.

    • For .FP8 models, ensure you select a profile backed by NVIDIA H100 or compatible Ada Lovelace nodes.

  3. Review Limits: The wizard will pre-fill CPU and Memory requests. Do not lower these below the recommended defaults unless you have strictly tested the memory pressure.

Step 4: Validate the Deployment

Click Deploy. You will be redirected to the Model Serving page.

Do not trust the "Green Checkmark" immediately. Verify the infrastructure state:

  1. Check the Status: Wait for the status to turn from "Deploying" to "Loaded" (Green).

  2. Verify the Endpoint: Copy the Inference Endpoint URL.

  3. CLI Validation: Run the following to confirm the Pod is stable and not crashing due to OOM (Out of Memory):

# Replace with your project name
oc get pods -n my-llm-project

# Check for restarts (indicates OOM or config errors)
oc get pods -n my-llm-project -o wide

Summary of Configuration

You have successfully: 1. Selected a verified asset from the catalog. 2. Prevented a DNS failure by shortening the resource name. 3. Aligned the deployment with a compatible hardware profile.
